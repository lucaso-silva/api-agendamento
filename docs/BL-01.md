**Guardian Review**

A BL-01 existe porque o único teste que sobe o Spring inteiro (`AgendamentoApplicationTests`) herda `application.properties`. Hoje isso o faz tentar conectar a:

`jdbc:postgresql://localhost/db_agendamentos`

usando `PG_DB_USER` e `PG_DB_PASSWORD`. Portanto, `mvn test` falha sem um PostgreSQL local já preparado — e, se ele existir, as migrations e testes podem atingir o banco de desenvolvimento. Isso viola isolamento, reprodutibilidade e segurança dos testes.

O que já existe:

- `application.properties` configura PostgreSQL, Hibernate em `validate` e Flyway.
- Flyway possui migrations `V1__cria_tabelas.sql` e `V2__insere-dados-iniciais.sql`.
- Há um teste de contexto com `@SpringBootTest`, que realmente precisa de banco.
- Os testes de `CriarAgendamentoImpl` usam Mockito e não precisam de Spring nem banco.
- Ainda não há perfil/configuração específica de teste, teste de migration, nem teste de repositório.
- O `pom.xml` tem drivers/configurações para PostgreSQL em runtime, mas não há uma estratégia de PostgreSQL isolado para testes configurada.

Camadas e arquivos provavelmente envolvidos, sem necessidade de mexer no `core`:

| Área | Papel provável |
|---|---|
| `pom.xml` | Dependências e suporte à estratégia de banco de teste |
| `src/test/resources/application-test.properties` (ou YAML equivalente) | Configuração exclusiva para testes |
| `AgendamentoApplicationTests` | Ativar explicitamente o perfil de teste |
| Novo teste de repositório em `src/test/.../repository` | Confirmar JPA + Flyway + PostgreSQL reais |
| Novo teste de migration | Garantir que schema vazio recebe as migrations |
| `README.md` ou `docs/` | Documentar a decisão e como executar testes |

A decisão técnica mais importante é a estratégia do banco:

- **Testcontainers + PostgreSQL:** cria um PostgreSQL descartável em container. É a opção que melhor reproduz produção e atende diretamente ao critério “PostgreSQL de teste”; requer Docker disponível.
- **PostgreSQL separado/local:** possível, mas ainda exige preparo manual e é mais fácil apontar por engano ao banco de desenvolvimento.
- **H2:** simples e rápido, mas não testa PostgreSQL de verdade; tipos, SQL e comportamento de migrations podem divergir. Eu não a escolheria para este requisito.

Conceitos essenciais:

- **Perfil Spring:** permite aplicar propriedades exclusivas em testes, sem contaminar desenvolvimento.
- **Flyway:** aplica migrations versionadas em ordem; um teste de integração deve permitir que ele crie o schema num banco vazio, nunca alterar migrations já existentes.
- **Teste de contexto:** prova que a aplicação consegue iniciar com suas integrações.
- **`@DataJpaTest`:** sobe somente a fatia JPA/repositórios, mais rápido que `@SpringBootTest`; é apropriado para testar persistência.
- **Testcontainers:** o ciclo de vida do banco fica sob o teste; ele começa vazio, recebe migrations e é destruído ao fim. Isso reduz o risco de tocar dados de desenvolvimento.
- **Segurança:** a configuração de teste deve usar banco efêmero/isolado e não registrar credenciais. Para esse primeiro item, não há razão para modificar domínio, DTOs, controllers ou migrations de produção.

Sugestão de tarefa pequena inicial: **definir e documentar a estratégia de banco de teste, e fazer apenas o teste de contexto usar essa estratégia.**

Critérios de aceite dessa etapa:

- O teste de contexto não lê a URL do banco de desenvolvimento.
- As credenciais/URL de desenvolvimento não são necessárias para executar os testes.
- Flyway permanece habilitado no ambiente de teste.
- A escolha fica documentada.

Testes a escrever antes ou junto:

1. O `contextLoads` usando o perfil/configuração de teste.
2. Depois, um teste JPA que persista e leia uma entidade/repositório.
3. Por fim, um teste que comece com banco vazio e verifique que as migrations foram aplicadas.
